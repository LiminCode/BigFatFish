# PR 报告：气泡配图按原始大小显示，尺寸上限可设

> **基线**：`f549917`（fix(voice): 语音合成端点握手被拒时换到另一个端点）
> **分支**：`feature/claude-session-fish`　**日期**：`2026-10-12`
> **范围**：15 个文件（实现 8、测试 5、文档 2 含本报告）

## 一、核心特性

用户往配图目录里加了很多大小不一的图片和动图，提出：气泡大小是固定的，应该尽量按图片
的原始大小显示，再设一个气泡大小上限，并且上限可以设置。

**改动前的行为**（实测，用户真实目录里的 72 张图，尺寸从 300×317 到 2308×3929）：
不论原图多大，都被缩放进一个固定的框——标准气泡是 220×140，吐气水泡是 150×122——
小图还会被放大去填它。

**改动后**：配图按原始大小显示（一个图片像素对应一个逻辑像素，再乘「配图大小」百分比），
长边超过「配图尺寸上限」才等比缩小，不放大。气泡跟着图片的大小走。

| 用户的 72 张图，画出来的尺寸（中位数） | 改动前 | 改动后（上限 420） |
|---|---|---|
| 吐气水泡（用户在用） | 108×108 | 200×200 |
| 标准气泡（纸感卡片） | 140×140 | 420×420 |

新增设置「互动 → 配图尺寸上限」，160～800 像素，默认 420。原有的「配图大小」保留，含义
改为「相对原始大小的比例」。

**顺带解决**：运行期间新放进配图目录的图片，此前要重启桌宠（或改一次设置）才会被收
进来——目录只在加载设置时列一次。现在每次自言自语前的检查（最多每 60 秒一次）会把目录
重新列一遍。

**红线 / 不变量**

- 不传上限的调用方行为不变（`test_without_a_limit_the_old_fixed_box_still_applies`）：
  旧的 `PetWindow` 路径仍是固定框口径，按 `AGENTS.md` 那条路径只修崩溃。
- 只缩不放：比上限小的图保持原样，包括在吐气水泡里不为填满安全区而放大。
- 解码缓存只留到「实际能画到的尺寸」，不因为上限调大而无谓占内存（见 §四）。

## 三、实现要点

**「原始大小」的口径。** 一个图片像素对应一个逻辑像素，与浏览器显示图片相同。在 125%
缩放的屏幕上这意味着图片被物理放大 1.25 倍；选它而不是「一个图片像素对一个物理像素」，
是因为后者会让同一张图在不同缩放的屏幕上显示出不同的尺寸。

**吐气水泡的上限约束的是整个水泡。** 标准气泡基本就是图片加一圈边，上限约束图片即可。
吐气水泡是一块固定比例（240:195）的画布，图片只能放在中间的安全区。按用户说的「气泡
大小上限」，上限管的是水泡的宽度。

**安全区比例是量出来的。** 原代码按「安全区占宽 65%、高 66%」估算水泡要多大，但实际
几何里安全区是按水泡主体的外接框再内缩得到的。用极宽、极高的图在 240～600 宽的水泡上
量，结果恒定：宽 55%、高 58.5%。按 65% 估算时，一张 120×90 的小图会被塞进装不下它的
水泡里画成 103×78——新代码第一次跑测试就是红在这里。

**缓存按实际画到的尺寸留。** 配图由后台线程预先解码并缩小后放进缓存。最初按「上限 ×
DPR」留像素，实测用户这 72 张图要 77 MB（改动前 23 MB）。但吐气水泡里图片最多只画到
水泡宽的 55%，按上限留有一大半像素永远画不出来。改成按 `image_display_edge` 留之后是
25 MB。有一条测试专门守「缓存留的像素不少于气泡真正画出来的」，防止这个优化把图弄糊。

**判断「是不是原始大小」不需要另存原图尺寸。** 解码线程只缩不放，所以缓存里的图要么是
原始尺寸（比缓存目标小），要么已经大于等于上限。两种情况下 `min(缓存图尺寸, 上限)` 都是
对的。

**设置准入记录**

```text
                      含义从「相对固定框的比例」变为「相对原始大小的比例」

```

## 四、性能分析

**方法**：一次性脚本（会话内，未入库）读用户真实的配图目录
`assets/big_blue_fat_fish`（72 张：48 jpg、14 png、10 gif），按解码线程同样的缩放规则算
缓存占用（`QImage.sizeInBytes` 之和）。屏幕缩放按用户的 125%。环境：Windows 11
10.0.26300，Python 3.13.15，PySide6 6.12.0。

| 配图缓存占用（72 张，DPR 1.25） | 缓存长边 | 内存 |
|---|---|---|
| 改动前（配图大小 100%） | 303 px | 22.8 MB |
| 上限 420，吐气水泡（用户现在的设置） | 318 px | **25.1 MB** |
| 上限 420，标准气泡 | 578 px | 77.1 MB |
| 上限 240，吐气水泡 / 标准气泡 | 182 / 330 px | 8.2 / 26.9 MB |
| 上限 600，吐气水泡 / 标准气泡 | 454 / 825 px | 49.0 / 145.6 MB |
| 上限 800，吐气水泡 / 标准气泡 | 605 / 1100 px | 83.9 / 233.6 MB |

| 其它指标 | 实测 |
|---|---|
| 72 张图全尺寸解码一遍（后台线程做的事） | 1.00 s |
| 真实桌宠重启 20 秒后的工作集 | 310 MB（没有同条件下改动前的数字可比） |
| 新测试文件 | 20 条 2.3 s |

**结论**

1. **稳态开销**：对用户当前的设置（吐气水泡、上限 420），缓存多 2.3 MB。
2. **新增路径**：内存随上限和样式变化很大——标准气泡下默认上限就是 77 MB，调到 800 是
   234 MB。设置行的说明里写了「数值越大，配图占用的内存越多」，但没有做硬性保护。
3. **新的系统调用 / 网络 / 磁盘 / 线程**：自言自语前的清单复查从「对每张已知图片各做一次
   存在性检查」变成「列一次目录」，仍是最多每 60 秒一次；没有单独计时。无网络、无新线程。
4. **缓存何时重建**：上限、气泡样式、屏幕缩放、目录内容任一变化时重建一次（既有的签名
   机制，把上限和样式纳入了签名）。

## 七、已知限制与后续

- **内存没有硬上限**：标准气泡 + 大上限 + 很多图时缓存可以到两百多 MB（§四）。可以改成
  按需解码或限制缓存总量，本次没做。
- `.avif` 不支持。JPG 的 EXIF 旋转信息也没有处理（解码线程直接 `QImage(path)`），竖拍的
  照片可能横着显示——这是既有行为，本次没动。
- 吐气水泡里图片只占水泡的一半左右，同样的上限下比标准气泡显示得小。
- 旧的 `PetWindow` 路径不读这个设置。
- 「配图大小」的含义变了：以前 100% 是「刚好填满固定的框」，现在是「原始大小」。调过
  这个值的用户会看到尺寸变化。

## 八、风险与回滚

- **影响面**：所有配图气泡的显示尺寸都会变（多数变大），这是本次的目的。
- **新增配置键**：`self_talk_image_max_edge`。
- **回滚**：`git revert` 即可；配置里残留的键无害。
