# 决策记录（ADR）

一份 ADR 记一个**长期有效的决定**：当时面对什么、选了什么、因此要承担什么。它回答的是
「为什么是这样」，不是「怎么用」（怎么用在上一层的主题文档里）。

## 什么时候写

日常 PR 不写 ADR：三份交付证据写在 PR 描述里，机制变了就改对应的主题文档。
PR 满足下面**任意一条**才新增一份 ADR：

1. **新的功能域**：新增一个窗口、一条后台任务、一个外部集成，或者一个新的包 / 一组成套的模块。
2. **架构边界变了**：进程或线程模型、数据落盘的格式或位置、跨进程 / 跨账号的通道、对外协议。
3. **一个将来有人会想推翻的取舍**：两条都走得通的路选了一条，或者有意不做某件看起来该做的事。
4. **下线**：删掉一个功能、入口或一类代码，尤其是有意留下了一部分的时候。

修 bug、打磨界面、改文案、加一个小设置项，都不算。拿不准时问一句：
「半年后有人看到这段代码想改回去，他需要知道什么？」答案超过三句话就写。

## 怎么写

- 文件名 `NNNN-<英文短横线小写>.md`，编号顺延，不复用。
- 三节，标题逐字：`## 背景`、`## 决定`、`## 后果`。整份 60 行以内。
- 写决定当时成立的事实和理由，不写实现细节（那些会变，放主题文档）。
- 决定被推翻时不删旧的：新写一份，在旧的顶部加一行「已被 NNNN 取代」。
- 新增后在下面的表里登记一行（`tests/test_pr_report_discipline.py` 会检查）。

模板：

```markdown
# NNNN：<一句话说出决定>

日期：YYYY-MM-DD

## 背景

当时的问题和约束。

## 决定

选了什么。列出考虑过又没选的路，各一句为什么。

## 后果

因此变容易的事、变难的事、以后改代码时要守住的线。
```
