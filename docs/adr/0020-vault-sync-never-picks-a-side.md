# 0020：知识库同步不自动选边，没人点头不提交大动作

日期：2026-11-22

## 背景

个人知识库存着用户几乎所有的笔记，是最重要的一份数据。它有三个写入者：用户在 Obsidian / 编辑器里手改本地克隆、
肥鱼自己的功能（灵感记录、蒸馏镜像）、云端的 Claude 会话直接往 GitHub 提交。原来没有任何一步负责「把手改的东西提交并
推上去」，也没有一步定期拉取；2026-11-22 发现克隆落后远端 46 个提交。要加同步器，而且以后要定时自动跑。

自动同步一份多方写入的文稿，危险在两处：两边改了同一段时谁赢；一次误操作（插件清空了一个目录）被原样推上远端。

## 决定

- **冲突不自动解决。** 本地提交 rebase 到远端上有冲突就 `rebase --abort`：本地提交留着、工作区是用户的版本、远端不动，
  结果记成「等你」。同步器永远不用 `-X ours` / `-X theirs`，也不替用户编辑冲突标记。
- **没人点头，不提交大动作。** 要提交的改动里有删除、或一次超过 20 个文件，而这次运行不是用户明确要的——不提交，等审核。
  用户在页面上点「现在同步」并确认，就是点头。
- **其余情况自动提交。** 不为每次停笔都弹一次审核：私有仓库里多一个提交的代价近乎零，git 历史本身就是撤销栈；
  每次都要人点，「及时推上去」就落空了。
- **先提交再联网。** 本地提交断网也做得成；停笔的内容先成为一份快照，推不推得上去是后一步。
- **在半截状态上不动手。** 克隆正在 rebase / merge、索引被锁、分支没有上游：什么都不做，报出来。
- **所有 git 操作排一条队**（一把锁，一个同步器）。

考虑过又没选的：

- **留冲突副本**（同步盘的做法：`笔记 (conflict).md`）：同步能继续，但知识库里会长出副本，链接和索引指向哪一份说不清。
  先不做；以后可以作为一个选项。
- **让 AI 合并冲突**：两边都是用户的文字，合错了是无声的内容损失。可以以后做成「AI 提议、人确认」，不做成自动。
- **每次提交都先问**：见上，「及时」落空；留作设置里的一档（还没做）。
- **冲突时把本地提交也撤掉、退回成没提交的改动**：看起来「什么都没发生」，但那份改动就又只存在于工作区，
  下一次误操作就没了。

## 后果

- 冲突会让同步停住，直到用户出手；这期间本地提交不断累积也推不上去。所以冲突必须在页面上显眼，并说清下一步。
- 守卫的两个条件是粗的（数文件、看有没有删除）：大改名会被拦，一次改坏一篇长文不会。它防的是成批的误操作，不是内容错误。
- 以后给同步器加任何「更聪明」的合并，都得先推翻这份决定：新写一份，说明内容不会无声丢失。
- 定时同步上线时，自动运行不带「已点头」，手动运行才带；不许反过来图省事。
