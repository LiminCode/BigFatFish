# 0015：私有仓库是数据的家，本机磁盘只是缓存；每种落盘数据都要登记从哪恢复

日期：2026-11-15

## 背景

一次系统崩溃清零过配置（见 [0008](0008-durable-config-and-private-backup.md)），之后配置有了本地副本和可选的
GitHub 备份。但其余的东西仍然只在本机：AI 写的记忆文件、AI 工具自己的设置和技能、蒸馏的条目库、
git 忽略的工作文件。这些文件散在几个目录里，用户说不出 AI 记了什么、记在哪。
用户定的硬约束：本机硬盘整个报废后，买来新电脑，要能靠 GitHub 上的数据把工作环境完全恢复，设置和记忆照旧。

## 决定

- 用户自己的 GitHub 私有仓库是一切需要长期保留的数据的家；本机磁盘上的那份是缓存。
- 每种落盘数据都在**存储表**里登记：在哪、谁写、属于哪个账号，以及**恢复来源**——
  进了哪个私有仓库、能重新算出来、是密钥、要重新登录，或者还没有覆盖。
  「还没有覆盖」必须带书面理由。漏登记由守卫测试拦。
- 配置全景上每处存储都看得见：位置、内容、多久前备份过。
- 个人的数据进个人的私有仓库，公司的数据进公司的私有仓库并在 WSL 里操作
  （见 [0003](0003-two-accounts-two-channels.md)）。本仓库是公开的，不放任何用户数据。
- 同步只推白名单里的文件，推送前扫密钥，内容相同不提交；拉回覆盖前先留底。
- AI 工具自己的记忆和设置，同步到个人知识库仓库里一个点开头的目录，不另开仓库。
- 密钥加密后放个人私有仓库，解密用的主钥放用户的密码管理器。仓库里不放明文密钥。
- 会话原文不备份，只备份蒸馏出来的条目和 AI 写的记忆。
- 恢复是一条命令：先演练（列出会还原什么、缺什么），确认后执行。演练定期在临时目录里跑，结果显示在全景上。

没有选「把整个 AI 工具目录做成 git 仓库」：里面有凭据、缓存和上百兆的会话原文，黑名单迟早漏。
没有选「引入现成的 dotfiles 工具」：这些数据有账号归属、要审核、要在图上看得见，不是 dotfiles 的形状。
没有选「备份会话原文」：量大、私密，而且真正要留下的东西已经由蒸馏提取出来了。

## 后果

- 新增任何会落盘的功能，都要先回答「丢了从哪恢复」，答不上来不算做完。
- 备份不了的只能列进恢复清单让用户手动做：各账号的登录态、连接器授权、操作系统本身。
- AI 工具的项目记忆按项目的绝对路径存放；新机器的用户名或路径不同就对不上，恢复清单要记映射。
- 主钥丢了，加密的密钥就恢复不了，只能逐个重新申请。
- 没演练过的备份不算备份：恢复路径要有测试，并且至少在一个干净环境上真的走通一次。
