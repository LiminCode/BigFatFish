# 0002：上游的改动只挑拣，不整体合并

日期：2026-10-24

## 背景

上游发版很快，并且把十来个模块改成了目录包。本项目这边删了打包和更新器、改了程序名、做了界面语言和 Metro 设置页。
试算一次整体合并有 130 个文件冲突。

## 决定

不 merge 上游，按功能挑拣：

- 只拿用户点名要的功能，加上能干净 `cherry-pick` 的修复；一步一个提交。
- 每一步先把上游的测试搬过来，确认在我们的代码上是红的，再动实现。
- 不能干净挑的，取上游的最终版重新落地；同一个提交里混着不要的部分时只搬一半。
- 搬过来的东西按我们的约束改落点（例如时间信息不进 system，以免每分钟让提示缓存失效）。

明确不搬的清单和原因记在 [与上游的关系](../upstream.md)，下次同步不用重新评估，除非前提变了。

## 后果

- 与上游的差异会持续扩大，以后每次同步的成本只增不减。
- 上游的修复不会自动到达，需要有人定期看一眼上游改了什么。
- 改帧序列档位这类「搬过来就要全量重出素材」的改动，要按 [与上游的关系](../upstream.md) 里的步骤停着肥鱼跑。
