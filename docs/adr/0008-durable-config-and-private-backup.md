# 0008：配置写盘要刷盘并留一份完好副本；备份只进用户自己的私有仓库

日期：2026-11-13、2026-11-14

## 背景

一次系统崩溃把 `config.json` 写成了长度正确、内容全零的文件。肥鱼按默认值重建配置，用户的设置全部丢失，
连带默认关闭的功能悄悄消失。原来的写法是「写临时文件再改名」，没有刷盘。
本仓库是公开的，真实配置里有本机路径和服务地址。

## 决定

- 保存配置时先把临时文件刷盘（fsync）再原子替换。
- 每次保存前把盘上那份已知完好的配置硬链接成 `config.json.bak`。「完好」用内存里的标志判断，不读盘校验
  （在 Windows 上「先读再替换同一个文件」要多等约 4 毫秒）。
- 读配置失败时按顺序找回：`.bak` → 用户自己的 GitHub 私有仓库里的备份（只在启动时那一次）→ 默认值。
- 落到默认值时记下标记并暂停自动备份，直到用户手动备份或恢复一次：否则联网后会把默认配置推上去顶掉好的备份。
- 完整备份只进用户自己的私有仓库，走 GitHub 的文件接口。公开仓库里不放任何配置内容，代码里不写死仓库名。

没有选「往公开仓库放一份脱敏的默认配置」：用户要的是能直接拉回来的整份。
没有选「在本地克隆里提交」：最需要恢复的时候，往往正是这台机器出了问题。

## 后果

- 退回 `.bak` 会丢最后一次改动。
- 只有用户配置刷盘，其它状态文件有意不刷：丢了能自愈或代价小。
- 从备份恢复依赖有效的 Token；从没成功备份过就没有这一层。
- 配置模块在日志装好之前运行，里面不能调根 logger，否则整个进程的日志都不进文件。
